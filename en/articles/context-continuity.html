Keeping context across AI collaboration: my Planner / Worker practice

LichHsu · September 11, 2026

I started using a persistent Planner and Worker to reduce repeated background explanations and give planning, implementation, and review clear responsibilities.

A change often carries decisions already made: what is in scope, which behavior must remain, what has been tried, and what evidence counts as completion. Reconstructing that context at every handoff can lose constraints and duplicate completed work.

Keep a persistent pair

My basic setup uses two persistent Desktop conversations. Planner A prepares the objective and reviews the result. Worker B implements and verifies changes within scope. I retain control of direction, scope, and phase decisions.

  1. The user sets direction.Define the problem and its boundaries.
  2. Planner A prepares the handoff.State the change and completion conditions.
  3. Worker B implements and verifies.Report actual changes, results, and limitations.
  4. Planner A reviews the delivery.Accept the result against the agreed conditions, or request a specific repair.

I reuse the same A/B pair for the same objective. Later handoffs focus on new information and changes while retaining the working context. I can open either conversation to inspect progress or intervene.

Preserve context and keep checking

A persistent Worker may retain the context of previous repairs. It may also retain incorrect assumptions. Keeping the same conversation does not guarantee an accurate understanding of the current state.

Review still needs actual changes and current evidence. Check that tests ran after the last edit, that verification exercised the entry point being delivered, and that unverified behavior is clearly identified. A completion report starts the review; it does not replace it.

Here, working context means information retained in task conversations and handoffs. I do not treat it as a guarantee of cache hits, fixed costs, or complete memory.

The Planner needs scope limits too

An extra review layer does not automatically improve the result. If the Planner keeps adding abstractions, unrequested features, or new completion conditions, collaboration can become repeated rework.

I require repair requests to identify a specific unmet condition. Optional improvements stay separate from the current delivery. Once the agreed conditions pass, the objective closes. KISS and YAGNI constrain both planning and implementation.

Keep handoffs short and actionable

A useful handoff states what to change, where the scope ends, how to determine completion, and which constraints still apply. The Worker returns a change summary, verification results, and anything not yet confirmed.

If the report lacks enough evidence for a decision, fill that gap. If results differ because of versions, execution methods, or permissions, resolve those differences before deciding to change the code. This helps maintain scope instead of treating every inconsistency as an implementation defect.

What I can claim today

I have published this approach as the Desktop Thread Worker skill. It defines handoff, return, review, and stopping rules. It remains an experimental instruction-based workflow. Tool availability, message delivery, and model adherence affect its results.

I have not established through controlled comparisons that it is faster, uses less quota, or is more reliable than other configurations. For future evaluation, I would track first-pass acceptance, repair rounds, repeated issue types, and human intervention separately.

This article describes personal methods and observations. It is not a model benchmark. It excludes private work records, project details, and internal measurements.
